Opethon, Accessibility & Inclusion track

Most accessibility work ships without a number. A number beats a claim.

One command gives every entry the same automated WCAG 2.2 AA check and the same design-contract score. Each figure carries its denominator and the command that produced it. When the kit cannot stand behind a number, it prints null and names the reason.

Run it on your entry

./run-verification.sh https://your-entry.example

On Windows, .\run-verification.ps1 https://your-entry.example. Needs Node 22 or newer and Chrome, Edge, Chromium or Brave. Nothing to install.

Independent of Opethon's organizers. Built by VAI and offered to the track.

Five rules every number follows

  1. The denominator travels with the number. Every figure says whether its denominator was observed in the run or declared by someone. The kit reports observed figures only.
  2. A number the kit cannot stand behind prints as null. The reason prints beside it: a refused page, an HTTP error, a page that never settled, an engine file that fails its hash.
  3. Flags and findings stay apart. Engines raise flags. A flag becomes a finding only after re-measurement in the rendered page confirms it.
  4. What the rules cannot decide goes to a person. Items needing review are listed on their own and never counted as passes.
  5. Every report lists what it did not look at. The list below is printed at the end of every run.

What the kit cannot see

Automated rules cover part of WCAG. W3C's own guidance is that no tool alone can determine whether a site meets accessibility standards. The kit tells an entrant which automated checks their page passes, with receipts, and shows a judge where testing with people has to take over.

  • Whether people using assistive technology can finish the task the entry exists for
  • Whether alt text, headings, labels and error messages mean what they say
  • Anything behind a click: menus, dialogs, forms, signed-in states
  • Keyboard use across a whole task: focus order, traps, visible focus
  • What a screen reader announces
  • Cognitive load, plain language, caption quality
  • Pages other than the one scanned
  • Speed, which needs field data

The misfire slot

Entries that ship an input method, such as dwell clicking, switch scanning, gaze or EMG, get one more figure: the misfire rate, the activations a person did not intend per hour the input was armed. It comes from access-conformance, an open-source instrument, and it prints only after 15 minutes of observed exposure.

Run it on your entry

The kit is one folder: a runner, the pinned rules engine, this page and its receipts. It needs Node 22 or newer and a Chromium-family browser. Each run prints a summary and writes report.json with every rule, every measurement and the reason for any null.

A deployed entry

Scans the page at two widths in a fresh headless browser.

./run-verification.sh https://your-entry.example

A local build

Serves the folder on 127.0.0.1 for the length of the run. The contract engine takes domain names only, so its slot prints null here.

./run-verification.sh ./dist/index.html

A page behind a browser check

Open the page yourself in a browser started with a DevTools port, then attach. The report records that a session was used.

./run-verification.sh https://your-entry.example --attach 9222

Exit codes: 0 no automated violations, 1 violations found, 2 a WCAG number was withheld and the report says why, 3 the run could not start. The method, every parameter and every known engine weakness are in METHOD.md; setup steps are in README.md.
